# 0004 — Implementation plan

> Answers "how". If the plan contradicts the spec, the spec gets fixed first.

## Approach

Bottom-up, as in specs 0001 and 0002: the figures exist and are proven correct
before anything can ask for them, and no criterion is closed by reading a
workflow back.

1. **The views first** — the reporting half of `docs/architecture/data-model.md`,
   in migrations, with their signatures snapshotted. They are testable in pgTAP
   against the seeded household on the day they land, with no model, no workflow
   and no bot involved. This is the whole contract: everything above is wiring.
2. **The period vocabulary.** "For a period" is answered from a fixed enumeration
   — `this_month`, `last_month`, `month_of:YYYY-MM`, `this_year`, `last_year`,
   `last_7_days`, `last_30_days` — resolved to dates **in SQL**, in the
   household's timezone. Every spend view carries the period name as a column, so
   a question is a filter rather than a date calculation, and the previous
   period's figure is a column of the same row (R18) rather than a second call
   and a subtraction (R4).
3. **The read tools.** The answerable set is the read half of spec 0003's tool
   registry (ADR 0039), not a second mechanism: each answerable question is a
   declared tool with a parameter schema and a PostgREST path, and the model
   chooses among them by name (R5). Adding a view in a later slice means adding a
   tool here — which is what makes R2a mechanically checkable rather than a
   promise.
4. **The mapping prompt** (`prompts/question-mapping/`, ADR 0025) returns
   `{tool, parameters}` and nothing else. Its schema forbids a numeric field, so
   A14 is a property of the contract rather than a hope.
5. **Answer rendering** from the message catalogue in the member's language, with
   figures substituted from the view result. No workflow does arithmetic on money
   (ADR 0040).
6. **The digests** as their own workflows, on their own schedule, reading the
   same views — so R13's "can never disagree" is true by construction, not by
   review.
7. **Search, "why this category" and CSV export** last: each is one more view or
   one more column on an existing one, and none of them changes the path above.

## Alternatives considered

| Option | Pros | Cons | Decision |
|---|---|---|---|
| Fixed period vocabulary resolved in SQL, carried as a column on every spend view | One call per question; the previous period is a column so R18 cannot be forgotten; the model picks from an enum, which is what ADR 0029 asked of it; no date arithmetic anywhere outside the database | An unusual range ("the last ten days") is a refusal until a period is added, and adding one is a migration | **chosen** |
| Views parameterised by arbitrary `from`/`to` as PostgREST RPC functions | Any range answerable | The model has to produce dates, which is exactly the creativity R5 excludes; and it puts the aggregation in functions while the catalogue calls them views | rejected |
| Compute the period-over-period delta in the workflow from two calls | No new columns | Arithmetic on money outside the database, which R4 forbids and ADR 0040 calls a defect | rejected |
| Let the model write SQL against a read-only role | Answers anything | Un-reviewable, unbounded, and it makes the refusal path (R6) impossible to define — there is no set to be outside of | rejected |
| n8n's own schedule trigger with a cron expression for the digests | Simplest wiring; `telegram-poll` already uses one | The cron expression cannot know the household's timezone, which is a database row (ADR 0034), and a container that was down at 09:00 silently skips the week | rejected |
| Hourly tick; SQL decides whether a digest is due and unsent | The timezone stays where it belongs; a missed hour self-heals on the next tick; idempotent by construction | One cheap query per hour, and "sent" becomes state to keep | **chosen** |
| Digests generated by a model for nicer prose | — | R12 forbids commentary, ADR 0029 routes digests to no model at all, and it would make the digest disagree with an answer | rejected |

## Contracts and data

- **Views.** `v_period_spend`, `v_category_spend`, `v_category_spend_by_month`,
  `v_merchant_spend`, `v_merchant_spend_by_month`, `v_member_spend`,
  `v_member_spend_by_month`, `v_category`, `v_account`, `v_account_balance`,
  `v_liability_summary`, `v_unconfirmed`, `v_unconfirmed_summary`,
  `v_transaction_detail`, `v_transaction_search`, `v_period_reconciliation` —
  names and meanings fixed by `data-model.md`.
- **Every spend view** carries: the grouping key, `period`, `period_start`,
  `period_end`, `amount_minor`, `currency`, `previous_amount_minor`,
  `delta_minor`, `unconfirmed_amount_minor`, `unconfirmed_share`. Transfers are
  excluded in the view, never by the caller.
- **Every view is created `WITH (security_invoker = true)`**, so the caller's
  row-level security applies rather than the view owner's. A view without it is
  the rank-1 failure in ADR 0015's table, so it is asserted by impersonation, not
  by reading the DDL.
- **`v_account_balance`** carries `balance_minor`, `limit_minor`, `headroom_minor`
  — headroom is a column, not a view (`data-model.md`).
- **`v_transaction_detail`** carries `category_source` (`merchant_default` |
  `explicit` | `model`), `model`, `prompt_version`: R20 is surfacing what spec
  0003 already records, not recording something new.
- **Read tool declaration** (spec 0003's registry format): `name`, bilingual
  description for the prompt, JSON Schema for parameters, the PostgREST path and
  filters it resolves to, and the roles permitted. The registry is the answerable
  set; `docs/guides/talking-to-meow.md` is its rendering for people.
- **Mapping model output schema**: `{ "tool": <enum of registry names>,
  "parameters": <object> }`, `additionalProperties: false`, no numeric field
  anywhere in it.
- **`digest_run(member_id, kind, period_start, sent_at)`** — scheduling
  bookkeeping, deliberately *not* a view and not in the catalogue: it is not a
  figure about money, and putting it there would dilute what that catalogue
  promises.
- **`member.digest_weekly`, `member.digest_monthly`** (boolean, default true) —
  R15. `data-model.md`'s `member` row is updated in the same commit.

## Migration and compatibility

- Additive only: no table spec 0003 created is reshaped, and every migration has
  a `down`. Dropping the views leaves the ledger untouched.
- `v_period_reconciliation` exists from this slice but reports "not reconciled"
  everywhere until spec 0007 gives it something to read. Stated in the answer as
  such, never omitted — R17 requires the digest to state reconciliation status
  before reconciliation exists.
- Search uses `unaccent` and `pg_trgm` over note, merchant and capture text
  rather than a per-language stemmer: a transaction does not record which
  language it was written in, the household writes in two and mixes them, and
  merchant names are neither language. A GIN index keeps it inside the latency
  budget.
- The seeded household (spec 0001) is the fixture for every figure test; no real
  household data is committed (ADR 0015).

## Verification strategy

Figures are pgTAP against the seeded household: the view is compared with an
independent aggregation written in the test, never with itself. Everything above
the database is a real request through the running stack with the model gateway
stubbed (ADR 0015), asserting the rendered reply. Digest scheduling is tested by
moving the clock in SQL, not by waiting.

| Acceptance criterion | How we verify it |
|---|---|
| A1 | `scripts/test-answer-question.sh`: stubbed mapping returns `category_spend`; assert the reply carries the figure, the named period and the unconfirmed share |
| A1a | Same script, ranked question: assert the reply lists categories in descending order with each total, and that the ordering matches `v_category_spend` ordered by amount |
| A2 | The same question in Russian for a Russian-language member: assert the figure is byte-identical and the reply is drawn from `i18n/ru.json` |
| A3 | A question the stub maps to nothing: assert no figure in the reply and that it names what can be asked, from the registry |
| A4 | `scripts/test-view-figures.sh`: for each read tool, run it and query its view directly with `psql`; assert equality |
| A5 | pgTAP `db/tests/0NN_account_balance.sql`: `v_account_balance.balance_minor` equals the independent sum of that account's postings |
| A5a | pgTAP plus the answer script: holdings, liabilities, net position and headroom each answered from `v_account_balance` / `v_liability_summary`; assert the headroom reply names the limit it is measured against |
| A5b | `scripts/test-answerable-questions.sh`: every view present in the database has a read tool or an explicit committed exemption, and `talking-to-meow.md` matches the registry exactly. Fails when a later slice adds a view and no question |
| A6 | pgTAP: seed a period with a known unconfirmed mix; assert `unconfirmed_share` exactly; then assert the rendered answer states it |
| A7 | `scripts/test-digest.sh`: run the tick with the clock at Monday 09:00 household time; assert one digest per member with digests enabled, each in that member's language |
| A8 | Same script: render the weekly digest and the equivalent questions; assert every figure in the digest equals the answer's, from the same view |
| A9 | Same script with `digest_weekly = false` for one member: assert no message and no `digest_run` row for them |
| A10 | Same script against an empty period: assert a message is sent and is the catalogue's single "nothing recorded" line |
| A11 | `scripts/test-digest-heartbeat.sh`: same pattern as spec 0001's heartbeat test — prevent the digest, let the Kuma window pass, assert the alert |
| A12 | `scripts/test-digest-language.sh`: the rendered digest in both languages is checked against a committed list of forbidden accounting and judgement words; the templates themselves are checked, so a new string cannot smuggle one in |
| A13 | Point the gateway stub at a failure response: assert the reply is the catalogue's plain failure line, contains no digits, and nothing is recorded as an answer |
| A14 | `scripts/test-question-mapping.sh`: the recorded model response for every golden question is asserted to validate against the mapping schema and to contain no numeric value at any depth |
| A15 | The full answer path driven as a `hh_member` session: assert household-wide spending is returned (ADR 0016) |
| A16 | `scripts/test-digest.sh` with the clock set to Monday 08:59, 09:00 and 09:01, and to the 1st: assert exactly one weekly and one monthly send, that neither waits on reconciliation, and that the reply states the period's reconciliation status |
| A17 | The template test in A12's script also asserts every answer and digest template contains the previous-period placeholder; the figure test (A4) asserts the value equals `previous_amount_minor` |
| A18 | pgTAP over `v_transaction_search` with a seeded note, plus the search workflow end to end: assert the transaction is returned by a word from its note |
| A19 | pgTAP on `v_transaction_detail` for three seeded transactions — model, merchant default, explicit — plus the workflow reply asserting the model and prompt version appear only in the model case |
| A20 | `scripts/test-export-period.sh`: export a closed month as an admin; assert the CSV's own totals equal `v_period_spend` for that period, that it parses as RFC 4180, and that the same request as a non-admin is refused at the database |

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| A view is created without `security_invoker` and silently reads past row-level security | medium | Asserted by impersonation for every view, and the assertion is generated from the catalogue so a new view cannot be added without one |
| The fixed period vocabulary is too narrow for how the household actually asks | medium | R6 makes the refusal explicit and names what can be asked, so the gap is visible rather than a wrong figure; adding a period is one migration and one enum entry |
| The mapping model picks a plausible wrong tool | medium | The answer always states the period and the question it answered (the spec's own edge case), so a mismatch is visible; the golden set measures it and a regression blocks a prompt change (ADR 0025) |
| Digest and answer drift apart as views change | low | They call the same tools; A8 compares them every run, and view signatures are snapshotted |
| The hourly tick double-sends after a restart | low | `digest_run` is unique on `(member_id, kind, period_start)`; the insert is the send's gate, not its record |
| Search is slow once the ledger is years deep | low | GIN index, and the latency budget is asserted in the same test that proves the result |

## ADRs required

- **Reporting periods are a fixed vocabulary resolved in SQL.** It binds the bot,
  the app (spec 0006) and the forecast (spec 0009) to the same period names and
  the same timezone handling, and it is the reason the model is never asked for a
  date. Drafted with this slice.
- No new ADR for `security_invoker`: it is a schema rule, and it belongs in
  `data-model.md`'s Rules section alongside the signature-snapshot rule it
  extends.
